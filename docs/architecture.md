# 官方插件职责与依赖

插件是独立的安装和启用单位。源码中的 `internal/common` 是编译时复用的代码，不是需要安装的插件；分页查询、权限检查和注册事件重试等通用逻辑放在这里。核心负责用户、会话、插件运行、事件队列与数据隔离，不承担具体运营业务。

| 插件 | 职责 | 与其他功能的关系 |
| --- | --- | --- |
| `access` | 连接凭据、用户权益、流量和提醒条件 | 节点、订阅、套餐和兑换码共用；接收节点流量与审计暂停事件 |
| `nodes` | 节点、机器、分组和状态 | 读取访问账户；审计插件可选，存在时向节点提供阻断规则 |
| `subscriptions` | 模板、分流、客户端配置和订阅链接 | 读取节点与用户权益，品牌名称可选；模板转换与校验代码供迁移器编译复用 |
| `branding` | 站点名称和图标 | 登录、前台和后台共用 |
| `registration` | 注册及全局开放设置 | 独立于商业功能；OAuth 查询同一注册政策 |
| `oauth` | 第三方登录和绑定 | 已有账号绑定无需注册插件；新账号注册遵守注册政策 |
| `captcha` | 可选人机验证 | 登录、注册、找回密码和订阅验证共用，默认不安装 |
| `commerce` | 套餐、订单、余额和优惠 | 依赖访问权益；支付、推广和兑换码分别可选 |
| `payments` | 支付渠道和回调处理 | 商业站可选，校验商业订单并通过事件通知订单；不承担套餐或推广 |
| `affiliate` | 推广关系、返佣和提现 | 依赖商业订单与余额，但不默认安装 |
| `redeem` | 兑换码与兑换记录 | 依赖访问权益；余额兑换仅在商业钱包可用时出现 |
| `audit` | 流量审计、阻断和暂停 | 独立可停用；消费节点事件并提供规则给节点 |
| `support` | 工单、公告和文档 | 发出工单回复事件；没有邮件插件也可使用 |
| `notifications` | 批量邮件、邮件模板、队列和密码找回投递 | 可单独安装；接收工单、订单和通用通知事件 |
| `import-*` | 各旧面板的数据导入 | 各来源可单独安装，共用迁移代码和统一管理界面，不导入 OAuth 或第三方客户端数据 |

套餐和兑换码中的节点分组选择是可选的界面协作，不将节点插件作为这两个插件的强制依赖；没有节点插件时只能使用已有的分组标识，安装节点插件后可按名称选择。订阅实际需要节点数据，因此保留对节点的依赖。审计、支付和推广虽然围绕其他业务工作，但都提供独立的配置或接口，并可分别关闭，不应为了减少插件数量而强制装入基本功能。

跨插件操作优先使用受权限限制的内部接口或事件，业务数据由所属插件保存。重试的操作应使用稳定的业务标识去重。业务插件不能直接修改别的插件的数据；改变数据归属时，需提供独立迁移工具并保留旧记录与备份。

记录与事件需要同时生效时使用核心 `Commit`，订单、工单和支付不再各自维护通知发送标记。旧数据升级见[事件队列迁移](runtime-upgrade.md)。单条记录、用户查找和后台分页使用核心查询接口，业务只读取当前请求相关的数据。插件导入规则和公开路由目标均由声明提供，核心不识别具体业务插件名称。

邮件内容由通知插件统一渲染，各业务仅发送业务事件或 `notification.requested`。品牌名称通过公共读取接口复用；无需为模板或公共名称额外安装基础插件。订单列表和概览共享成交汇总口径，余额充值不重复计为套餐成交。兑换码的来源模板保留在迁移归档中，单码不重复保存完整来源模板。

用量提醒由 `access` 在自身的周期和到期逻辑中发出事件，用户偏好也归访问账户保存；`notifications` 在发送前通过受限接口核对提醒是否仍有效。邮件可选，访问账户不调用 SMTP，也不依赖商业插件。折抵规则、付费依据和金额结算归 `commerce`，`access` 只按已确认的权益版本执行替换及撤销，避免把钱包逻辑混入流量管理。
