# 商业运营接口与规则

`commerce` 提供套餐、订单、余额和订单价格优惠。在线收款由 `payments` 提供，访问权益由 `access` 提供。当前开发版本为 `0.0.1`，需要当前构建的核心及相关插件。

普通注册由独立 `registration` 插件提供，推广佣金与提现由可选 `affiliate` 插件提供，兑换码由独立 `redeem` 插件提供。公益或分享站点可以只安装注册、访问、节点、订阅和兑换码功能，无需安装商业交易或推广插件。

## 模式与注册

商业模式安装所需插件后，核心发送 `workspace.configured`。商业插件据此保存当前工作空间模式；切换为自用时，公开套餐关闭，原有订单、余额和套餐数据保留。管理员仍可管理已安装的商业插件。

商业插件不再提供注册表单、注册开关、推广设置或兑换入口。注册和推广的安装、启用与设置相互独立；个人折扣仍参与订单价格计算。

## 金额与期限

接口金额使用百分之一单位的整数，例如 `999` 显示为 9.99 个站点单位。管理员在“金额设置”调整单位名称和符号；仅影响显示，不换算余额、订单或支付金额，也不改变支付渠道的结算币种。前端提交订单后，以返回订单的实际 `amount` 作为支付金额。

套餐使用以下期限字段：

| 字段 | 含义 |
| --- | --- |
| `durationUnit=month` | `durationValue` 个日历月，月末不足时取当月最后一天 |
| `durationUnit=day` | `durationValue` 天 |
| `durationUnit=permanent` | 长期有效 |
| `quotaGiB` | 每周期流量，单位 GB |
| `unlimited` | 显式表达不限流量；额度为 0 不等于不限 |
| `timezone` | 计算日历月使用的时区，普通新套餐默认 `UTC`，导入套餐保留源时区 |
| `kind` | `subscription` 订阅、`time` 延长时间、`traffic` 流量加包、`reset` 重置用量 |
| `enabled` / `visible` | 是否允许新购、是否在公开目录展示；公开目录只展示同时满足两项的套餐 |
| `renewable` | 已有相同 `planFamilyId` 权益的用户是否可以续费，停售或隐藏套餐也可单独允许原用户续费 |

一个套餐可设置多个 `periods` 购买选项。每项包含稳定的 `id`、`label`、整数分 `price`、`durationUnit`、`durationValue` 和 `kind`；可单独设置 `resetPolicy` 和 `enabled`、`visible`、`renewable`、`reviewRequired`。周期的开关在套餐总开关基础上进一步限制；同套餐续费依套餐及该周期的续费开关判断。重置流量选项使用 `kind=reset`，长期选项可设置独立的重置规则。没有周期数组的旧单周期套餐仍可使用，并以原套餐 ID 作为其周期 ID，升级时应转换为新结构。

未到期的订阅续费从现有到期日延长，已到期则从购买时延长。同一 `planFamilyId` 的周期套餐续费保留当前周期用量；更换套餐按新权益处理。套餐内的重置规则随权益下发，长期套餐可使用不自动重置规则。

新套餐自动建立套餐族标识。仅延时、流量加包和用量重置需要用户已有访问账户；没有基础套餐时下单会直接提示，不会先扣款再发现无法开通。待核对的迁移套餐不能购买或续费；管理员核对后，需要明确取消套餐及相关周期的待核对标记，并按需启用套餐和周期。

## 公开套餐

无需登录：

```http
GET /api/v1/extensions/commerce/public/plans
```

只返回已上架套餐及其可公开购买的 `periods`；每个周期提供标识、名称、价格、期限和类型。不会返回迁移原记录、购买限制对象或内部来源信息。非商业工作空间返回空列表。`GET /plans?scope=mine` 按当前用户资格过滤可购买或续费的周期，管理员在用户前台预览时也使用此参数。

公开接口不创建订单。购买需要用户先登录。

## 创建与支付订单

普通用户只为自己下单；管理员可以明确填写 `userId` 代建订单。

```http
POST /api/v1/extensions/commerce/orders
Content-Type: application/json

{
  "planId": "套餐ID",
  "periodId": "购买周期ID",
  "coupon": "可选优惠码",
  "requestId": "一次购买意图对应的唯一标识"
}
```

充值订单使用 `kind=recharge` 和整数分 `amount`：

```json
{
  "kind": "recharge",
  "amount": 5000,
  "requestId": "一次充值意图对应的唯一标识"
}
```

同一用户用相同 `requestId` 重试相同内容时返回原订单。相同标识更改套餐、周期、金额或优惠码时返回 `409`。用户修改输入应创建新的标识；网络失败且输入未变化时复用原标识。多周期套餐必须指定 `periodId`；仅有一个周期时可以省略。后台按周期创建订单时也可仅传唯一的 `periodId`。

订单创建会计算有效优惠码与个人折扣，保留减免金额。个人折扣按所选周期原价计算，最终应付最低为 0。订单保存所选周期的价格、期限、类型和重置规则快照，后续修改套餐不会改变已有订单的权益。

待支付订单默认在创建 30 分钟后自动取消，后台订单列表的“订单设置”可调整 `paymentTimeoutMinutes`，单位为正整数分钟。修改即时影响仍待支付的订单，已取消的订单不恢复。后台任务约每分钟检查一次；余额支付、确认收款和在线收银台也会检查截止时间。已经扣过余额的订单继续开通，已付款订单不按未付款取消。超时后才收到的在线款项进入支付核对，不重复发放权益。

取消保留订单记录，写入 `canceledAt` 和 `cancelReason`（`timeout` 或 `manual`）。待支付订单响应中的 `expiresAt` 是按当前设置计算的支付截止时间，付款弹窗会显示该时间。

后台支持按状态、类型、支付方式、用户、创建时间和取消原因组合筛选，筛选与分页、总数、关键词搜索在服务端一起执行。管理员还可按用户邮箱或姓名搜索。`GET /orders` 接受 `status`、`kind`、`method`、`cancelReason`、管理员专用 `userId`，以及 RFC3339 格式的 `createdAtFrom` / `createdAtTo`；时间范围包含两端。普通用户的筛选始终保留自身归属条件。

| 接口 | 用途 |
| --- | --- |
| `GET /orders` | 当前用户的订单；管理员可查看全站订单 |
| `GET/PATCH /order-settings` | 管理员读取或调整待支付有效期，正文为 `{"paymentTimeoutMinutes":30}` |
| `POST /orders/{id}/pay` | 使用余额支付套餐订单 |
| `POST /orders/{id}/cancel` | 取消待支付订单 |
| `POST /orders/{id}/confirm` | 管理员确认已人工收款 |
| `POST /orders/{id}/refund` | 管理员将已完成套餐订单退回余额并撤回可撤回权益 |
| `POST /api/v1/extensions/payments/checkout` | 在线渠道创建收银台，提交 `orderId` 与 `channelId` |

充值需要在线渠道或管理员明确调整余额，不能用余额给余额充值。成功支付后依次写入已支付状态、开通权益并完成订单；中途失败会通过任务重试，权益和账本按业务标识避免重复写入。

余额扣款完成但订单状态尚未写回时，后台任务会继续开通，订单不能再取消。单笔订单开通或退款失败不会阻塞其他订单。兑换码的归属、次数与入账重试由独立兑换码插件负责。

在线支付记录以支付渠道和外部交易编号去重。已取消订单收到款项，或余额支付和在线支付同时到账时，额外收款进入支付记录的“待核对”状态，不会再次开通权益。管理员核对实际收款后处理原渠道退款或余额调整。

后台订单的支付渠道选项由浏览器直接读取支付插件，插件间不在同一处理链中反复互相等待。停用支付插件时，用户仍可按现有余额支付套餐。

退款会检查较新的权益开通顺序，避免撤回较早订单时覆盖后来购买。充值余额的原渠道退款仍由管理员核对处理，不能把已花掉的充值直接从账户再次扣走。

## 独立插件与内部接口

推广记录、佣金、提现及个人返佣规则由 `affiliate` 管理，见 [推广插件](affiliate.md)。未安装或停用推广插件时，商业订单正常购买、支付、开通和退款，不产生新的推广佣金。

兑换码由 `redeem` 管理。只有余额类型的兑换码需要商业钱包；流量与期限类兑换码可以在未安装商业插件的站点使用。钱包页面不再重复放置兑换入口。

商业插件为受信任的推广和兑换码插件提供：

| 接口 | 作用 |
| --- | --- |
| `GET /internal/capabilities` | `affiliate`、`redeem` 检查钱包入账能力，返回 `walletCredits=true` |
| `POST /internal/wallet/credits` | 仅 `affiliate`、`redeem` 按稳定操作标识增加用户余额 |
| `GET /internal/orders?userId=...` | 仅 `affiliate` 查询指定用户的订单基本信息，用于首购判断 |
| `GET /internal/purchase-history/{userId}` | 仅 `affiliate` 查询迁入订单归档之前的购买事实；不把当前新订单计入该标记 |
| `GET /internal/orders/{id}` | `payments`、`affiliate` 核对订单状态 |

路径以 `/api/v1/extensions/commerce` 为前缀。内部钱包请求为 `{userId, amount, operationId, reason}`，`amount` 为正整数分。相同来源插件与 `operationId` 重试同一用户、金额时不重复入账；变更用户或金额返回冲突。普通用户不能调用，管理员调整余额仍使用原余额账本操作。

商业插件发布 `order.fulfilled` 和 `order.refunded`。接收者须核对事件来源 `commerce`，并按 `orderId` 去重。开通事件包含 `userId/amount/planName/kind/paidAt/fulfilledAt`，退款事件包含 `userId/amount/refundedAt`。通知发布失败会继续重试，不会重新扣款或重复发放访问权益。

## 数据保留

商业模式与自用、分享之间切换不会清空商业数据。停用插件会停止其业务处理；卸载插件保留核心业务记录。备份应包含完整核心数据目录，正式迁移前另行保留源系统完整数据库和配置备份。

Xboard / V2Board 的订单和优惠码可通过迁移插件转换到本模块，不重新扣款或发放权益。支付配置和审计规则仅归档。详见[迁移文档](migration.md)。

从 1.3.x 升级前，停止面板并按 [推广插件迁移说明](affiliate.md#从旧商业插件拆出数据) 将旧推广数据搬入独立插件；兑换码按兑换码插件文档搬移。旧商业接口不保留别名，旧财务记录保留金额和编号，已有余额不重复入账。
